# How AyuNidan works — the full user pipeline

This is the walk-through of what happens from the moment you open the app to the moment you read the dashboard.
(`ARCHITECTURE.md` is the reference version; this one follows a single user session.)

## 0. Two processes must be running
| Process | Command (folder) | Address |
|---|---|---|
| Backend API | `npm run dev` (`AyuNidan backend`) | http://localhost:8080 |
| Frontend | `npm run dev` (`AyuNidan frontend`) | http://localhost:3000 |

A message like *"We couldn't reach the server"* (formerly the browser's "Failed to fetch") means the frontend could not reach the backend; the technical detail is printed in the browser console:
the backend is stopped or restarting, `NEXT_PUBLIC_API_URL` is wrong, or the page's origin is not in the backend's CORS list.
Live voice dictation works without the backend because it runs inside your browser — only sending anything to the server needs the API.

## 1. Login
`/login` → email/password (or Google). The backend returns a JWT; the browser stores it and sends it as `Authorization: Bearer …` on every request.
Every record you create is owned by your user id; nobody else can read it.

## 2. New consultation (`/consultation/new`) — three ways to give input

### A. Upload PDF / PNG / JPG → `POST /api/uploads` (Job A: understand the document)
1. **Validation** – must be logged in; rate-limited; file type is checked by MIME, extension **and** the file's real bytes; size/count limits.
2. **PDF** – parsed locally, page by page: text layer, lab tables (rows kept with page + table id), scanned pages and embedded images detected.
   Text PDFs are sent to the model as *text*; only scanned/image content is attached for the multimodal model.
3. **PNG/JPG** – sent to the multimodal Gemini model, because there is no local OCR. Whatever it reads is labelled *model-transcribed, unverified*.
4. **One structured extraction call** (schema-constrained): patient details, symptoms, medicines, lab values (unit/range/flag/date), dates, diagnoses written in the document, measurements, imaging findings, doctor notes, limitations.
   Table rows found by the local parser override the model's version of the same lab.
5. **Indexing** – the text is chunked (tables row-intact), embedded **locally** with BGE-small, and stored in *your* private Pinecone namespace; a Mongo record tracks ownership.
6. The response fills the big text box with the transcription/symptoms/medicines, so **you can read and edit it**. Nothing is assessed yet.

### B. Voice note (mic button)
- Browsers with speech recognition (Chrome/Edge): a **live transcript** panel shows grey *interim* words and black *final* words. Only final words are added to the text box when you stop. Cancel discards everything.
- Other browsers: audio is recorded and sent to `POST /api/voice/transcribe` (validated; transcribed by Gemini); the final transcript appears after you stop. It says it isn't live.

### C. Type directly in the text box.

## 3. "Generate Clinical Summary" → `POST /api/consultations` (Job B: assess from evidence)
1. Your text and the reviewed extraction (labs, table report, document ids) are saved **first** with `status: processing` — so a failure never loses your input.
2. **Retrieval** – up to 6 short queries are built from the findings (abnormal labs first). Each is embedded locally and searched in (a) your own document chunks and (b) the separate verified-reference knowledge base. Weak matches are dropped (thresholds 0.68 / 0.66); the rest are trimmed to a size budget and labelled **F#** (your findings), **P#** (your documents), **R#** (references).
3. **One LLM call** (LangChain prompt, structured output). The model gets *only* that evidence, is told to treat it as data (not instructions), and must return: risk level (`low | medium | high | insufficient_evidence`), summary, key findings with evidence ids, uncertainty.
4. **Server-side checks** – any evidence id the model invented is dropped; if nothing valid is cited, the result becomes `insufficient_evidence`; the score is kept consistent with the level.
5. The record becomes `completed` (or `failed` with stage + reason if any step broke) and you are redirected to the dashboard page for that consultation.

## 4. What you see on the consultation page (`/consultation/<id>`)
| Section | Meaning |
|---|---|
| Header: risk badge + score | LLM triage label from the evidence. **"Not Assessed"** if AI failed, **"Insufficient Evidence"** if the evidence couldn't support a level. Never shown as low risk by mistake. |
| Patient block | Name / age / gender as extracted (and as you edited). |
| AI Assessment Summary | The assessment summary (with the "Generated by AI – Subject to Physician Review" line). |
| Extracted Lab Values | Test, value, range, flag; under each name: **where it came from** (file · page · table, or "model-extracted · location not verified"). |
| Evidence-Grounded Assessment | Key findings with F/P/R chips, the model's stated uncertainty, retrieval counts, and how many invented citations were rejected. |
| **Medical References Used** | Only references that were retrieved **and** cited: title, organization, section, page/version/URL when they exist, similarity, and the retrieved text (expandable). Empty (and says so) when no verified references are ingested. |
| Patient Evidence | The chunks of *your* documents that were cited (file, page, table). |
| Structured Report | Source documents with per-page status (text / scanned / mixed), full lab tables, dates, written diagnoses, measurements, image findings, doctor notes, and **extraction limitations**. |
| **Ask About This Report** | Type a question → `POST /api/documents/query`: retrieval from your report + references → one cited answer, split into "From your documents" and "Medical references used". If the evidence doesn't contain the answer, it says so. |
| Symptoms / Medications | Extracted lists. |
| Clinical Term Explainer (button) | Short glossary-grounded explanation of a term (`/explain`). |

The home page (`/`) lists your consultations (search by patient name) and the risk distribution; failed and insufficient-evidence records are shown separately from low/medium/high.

## 5. When something goes wrong (by design it is visible)
| Situation | What you see |
|---|---|
| Backend down / CORS blocked | "We couldn't reach the server. Please wait a moment and try again." toast (details in the browser console) |
| Model quota/timeout/outage | Upload toast with the failure; a saved consultation marked **AI FAILED / Not assessed** (input kept) |
| Not enough evidence | **Insufficient Evidence** state, uncertainty explained |
| Scanned page / image | Limitation listed under the report; values flagged model-transcribed |
| Other user's id | 404 / "insufficient context" — never their data |

## 6. Honest scope
Evidence-grounded preliminary triage aid for a clinician's review — **not a diagnosis, not clinically validated.** With no real reference corpus ingested,
the "Medical References Used" panel is empty and assessments rest on your own report's values and printed ranges.
